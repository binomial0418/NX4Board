# obdlab — Mac 直連 OBD 訊號分析

用 Mac 直接透過藍牙序列埠對話 ELM327 傳輸器，繞過手機 App，
把訊號逆向的回饋迴路從「好幾小時」縮到「幾秒」。

代碼對應表在 **[OBD_CODES.md](OBD_CODES.md)**，待辦與注意事項在
**[TODO.md](TODO.md)**。

## 為什麼要繞過 App

先前每一輪是：改 Dart → 建 APK → 安裝 → 上車測 → 匯出日誌 → 貼回來 → 分析。
一輪好幾小時。

而回顧那八趟實車，**大多數時間不是在找車上的訊號，是在找工具本身的錯**：

| 輪次 | 實際卡住的原因 |
|---|---|
| 1 | 押 Mode 21，這台車一條都不支援 |
| 2 | 監看一輪 145 秒，切檔停留幾秒取樣不到 |
| 3 | 雜訊過濾太弱，15 個候選裡 14 個是引擎自己在飄 |
| 4 | 點名只認正回應，把 770 判成不存在 |
| 5 | 掃描期間監看停擺，測試落在 909 秒盲區 |
| 6 | 實驗沒有對照組，開門下車的訊號淹掉真正的目標 |

每一個都是幾行程式的問題，但每一個都花掉一趟實車。迴路縮短之後
這些在第一分鐘就會現形。

## 架構

```
Mac ──BLE（CoreBluetooth）──► ELM327 傳輸器 ──OBD-II──► 車輛 CAN
 │
 ├── ble.py       BLE 傳輸層，直接呼叫 CoreBluetooth
 ├── daemon.py    常駐連線，指令走 Unix socket 進來
 ├── elm.py       ELM327 初始化序列、回應整理
 ├── uds.py       UDS 請求判讀、負回應、Mode 01 逐區塊走訪
 ├── discover.py  模組點名、家族探索、DID 掃描
 ├── snapshot.py  快照拍攝與四道過濾的比對
 ├── store.py     JSON 持久化，中斷了不用重來
 └── run.py       指令列入口
```

唯一的硬體需求是**車上要有 Mac**。傳輸器不用換，就是現在那顆。

### 為什麼是 BLE 不是序列埠

原本打算走傳統藍牙序列埠，實測不可行。`/dev/cu.Android-Vlink` 在配對後
一直存在，開埠瞬間成功（0.00 秒），但寫入不會觸發 RFCOMM 連線，
`system_profiler` 全程顯示 Not Connected。只有在系統設定裡手動按連線
那條鏈路才會起來，而且閒置就掉。macOS 沒有提供從指令列建立 SPP 連線的
介面，`blueutil` 之類的工具也做不到。

BLE 的 central 角色可以完全程式化，這個限制就消失了。代價是要自己處理
CoreBluetooth 的執行緒模型，細節寫在 `ble.py` 的開頭。

也沒有用 bleak：它 1.1.1 版在這台機器上會誤報「Bluetooth device is
turned off」，原因是它在主執行緒上阻塞等一個需要主執行緒才送得到的
狀態回呼，自己鎖死自己。

## 開始使用

先在 macOS 系統設定把 OBD 傳輸器配對成藍牙裝置。配對成功後
`/dev/cu.<裝置名>` 才會出現。

```bash
cd obdlab
python3 run.py ports          # 確認序列埠出現了
python3 run.py probe          # 連線、跑初始化、印 ELM 版本
```

不需要安裝任何套件。BLE 走 `pyobjc` 的 CoreBluetooth 綁定，
macOS 上的 Python 本來就有。

## 指令

| 指令 | 作用 |
|---|---|
| `ports` | 列出候選序列埠 |
| `probe` | 連線並跑初始化 |
| `raw 22BC08 --header 770` | 送一道原始查詢，印原始與判讀 |
| `modules` | 模組點名（正回應與負回應都算存在） |
| `families 7D0` | 對某個位址做家族探索 |
| `sweep 7D0 E0` | 掃一個家族的 00~FF |
| `discover` | 完整探索：點名 + 家族 + 掃描 |
| `pids` | 標準 PID 支援表，含多模組聯集 |
| `snap 鑰匙在車內` | 拍一張快照（`--delay 60` 可延遲啟動） |
| `diff` | 比對已存的快照 |
| `watch 770\|22BC08 7E0\|22E000` | 即時監看，只印變動 |

共用選項：`--port` 指定序列埠，`--verbose` 印出每一道收發。

## 比對怎麼運作

`snapshot.py` 的四道過濾，每一道都是實車踩過的坑：

1. **長度不一致就略過** — 多幀組裝結果不同時比 byte 會全錯位
2. **連讀兩次就變的算雜訊** — 引擎溫度、點火角、滾動計數器屬於這類
3. **同標籤跨快照不穩定的算雜訊** — 抓的是比連讀間隔更慢的漂移，
   所以每個狀態要拍兩張
4. **識別區變了是警訊不是候選** — 那裡永遠不變，變了代表讀取有問題

排序把**單一位元翻轉排前面**。旗標只翻一個位元，量值會翻好幾個。

`snapshot.py` 有內建自我測試，用已確認的 R 檔訊號加上已知的引擎雜訊
餵進去，驗證只留下正確答案：

```bash
python3 -c "
import sys; sys.path.insert(0,'.')
import snapshot  # 檢視 module docstring 裡的規則
"
```

## 與 App 的分工

App 是量產儀表，obdlab 是研究工具。obdlab 找到的結論以
「位址 + byte + 遮罩」的形式搬回 App，就像 `22BC08` byte F bit3
與 `22E000` byte N bit3 那樣。兩邊共用同一套初始化序列與判讀規則。
