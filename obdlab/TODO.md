# TODO 與注意事項

## 探索順序

使用者指定的優先序。五項都是**可以停著不動、維持住的狀態**，所以做法一樣：
即時監看加事件標記，不用拍快照。快照一張要三分半，五個目標十幾種狀態根本
跑不完；監看 770 全家族一輪只要兩秒，而標記鈕已經證明夠精準（D 檔三次
切換全中，延遲都在 1.8 到 4.0 秒內）。

**建議一次坐下來做完。** 除了雨刷要先弄濕玻璃，其餘都是按按鈕轉開關而已。
先載入車身監看組、開專注監看、開始監看，然後依序走完下面五項，
每換一個狀態前先按「事件」標記。

### 1. 檔位 N 與 P

目前 R 與 D 都已上線，但 **P 與 N 分不出來**，兩者在所有已知旗標上都是 0。

- [ ] 踩住煞車，P → N → P → N 來回兩趟，每檔停 20 秒以上
- [ ] **注意煞車是個干擾項**。切檔一定要踩煞車，而 `770/22BC06` byte E
      遮罩 `0x2D` 就是煞車訊號，它一定會跟著動。判讀時要排除它，
      或者切到 N 之後放開煞車再停留一段，讓兩者分離
- [ ] 車門開關狀態全程保持一致，否則 `22BC03`/`22BC04`/`22BC08` 那組會混進來
- [ ] 已知的兩個對照：`770/22BC08` byte F bit3 是 R、
      `7E0/22E000` byte N bit3 是 D。這兩個在 P/N 之間都不該動，
      拿來確認監看確實在運作

### 2. 雨刷

`770` 驅動雨刷，而那裡還有四個位址完全沒解讀（`BC01` `BC05` `BC07` `BC10`），
另有三個位元組已知會動但沒有解釋：`BC05` byte F、`BC10` byte E 與 F。
`BC10` byte E 曾經是 `0xF0`，一次四個位元，形態上像多位置欄位。

- [ ] **先把擋風玻璃弄濕**。乾刮會磨傷玻璃也毀雨刷片
- [ ] 依序走完：OFF → 點動 → 間歇（延遲旋鈕每一段都試）→ 低速 → 高速 → OFF
- [ ] 後雨刷與噴水也各試一次
- [ ] **雨刷不是布林值**，是多位置欄位。比對排序把「單一位元翻轉」排前面，
      雨刷會被排到後面去，不要只看前幾名就下結論
- [ ] 自動雨刷的雨量感測器會給連續變動的值，會被雜訊過濾濾掉。
      濾掉的是感測器讀數，開關位置是穩定的所以還在

### 3. 示寬燈與日行燈

`22BC09` 的 byte G 目前遮罩是 `0xC0`，也就是 **bit 7 與 bit 6 兩個位元**。
所有樣本裡它們一直同進同出，但那可能只是因為從來沒有取樣過只開小燈的狀態。

- [ ] 轉到**只有小燈亮、大燈不亮**那一段，讀 `22BC09` byte G：
      - 變成 `0x80` 或 `0x40` → 兩個位元分開了，小燈到手
      - 變成 `0x00` → 小燈不在這個 byte，往別處找
      - 還是 `0xC0` → 那兩個位元真的是同一件事
- [ ] 順便測後霧燈、前霧燈（若有）
- [ ] 日行燈通常引擎一發動就亮、無法單獨關閉，可能測不出變化。
      如果它跟小燈共用電路，解出小燈就等於解出它
- [ ] **修掉 `(g & 0xC0) != 0` 這個判斷**。如果小燈佔其中一個位元，
      只開小燈時 App 會誤報大燈開啟，連帶讓 ESP32 儀表亮度提前變暗。
      等測出結果再改，不要先猜
- [ ] 小燈確認後接進亮度邏輯。自動頭燈是先亮小燈才亮大燈，
      螢幕亮度跟著小燈走比跟著大燈走更早、更貼近實際光線

### 4. AUTO HOLD 狀態

- [ ] 兩種狀態要分開測：**功能已啟用（armed）** 與 **正在作動夾住（holding）**。
      按鈕按下去是前者，實際踩煞車停住後放開腳才是後者
- [ ] 流程：按鈕開啟 → 標記 → 踩煞車停住 → 放開煞車讓它夾住 → 標記 →
      輕踩油門解除 → 標記 → 按鈕關閉 → 標記
- [ ] **位置未知**。它由電子手煞車或車身穩定系統控制，而 `7D1`（`OBD.csv`
      標註是 ABS）點名沒回應。`7D4` 與 `7B1` 是有資料但用途不明的模組，
      是首要嫌疑。監看時要把這兩個也加進清單
- [ ] 煞車訊號同樣會干擾，判讀時要排除 `22BC06` byte E

### 5. 駕駛模式

- [ ] 依序循環 ECO → NORMAL → SPORT → SMART（依實車有的模式），
      每個停留 15 秒以上並標記
- [ ] **這也是多位置欄位不是旗標**，跟雨刷一樣會被排序壓到後面
- [ ] 位置可能在 `7E0` 引擎模組或儀表，不一定在 `770`。
      監看清單要放寬，或先拍一輪快照確定在哪顆模組

## 注意事項

### 安全

- **全程唯讀**。只送 `22`（ReadDataByIdentifier）與 `ATSH` 切換 Header，
  兩者都摸不到致動器。最壞情況是讓匯流排晚一點睡。
- **不要碰 `2F`、`2E`、`27`、`31`**。那些是致動與安全存取，
  車身致動的風險等級跟唯讀完全不同，而且門鎖那類幾乎一定被
  車廠專屬演算法鎖著，投入產出比極低。此事已與使用者確認不做。
- 長時間輪詢會把匯流排撐著不睡，會耗 12V 電瓶。做半小時沒問題，
  放整晚不行。

### 技術陷阱

- **負回應代表存在**。`7F 22 31` 是「我在，但我不支援這個 DID」。
  第一版點名只認正回應，把 770 判成不存在，而它整份日誌都在正常回答。
- **不要用字串搜尋定位 PID**。要照 PID 的固定長度逐段走訪。
  `indexOf('0B')` 會在 704~767 rpm 時把轉速低位元組當成 MAP。
- **廣播查詢要聯集**。`0100` 會有多顆模組各自回應，只取第一個會漏掉大半。
- **`ATAL` 不能省**。沒有它長回應會被截斷。
- **識別區是金絲雀**。`22F1xx` 永遠不變，它變了代表多幀組裝錯位，
  整份資料打折扣。不要把它當候選。
- **payload 前綴**。7A0、7E3、7E4 的 payload 前 4 個 byte 是有效性遮罩
  不是資料。解讀時先跳過。
- **`OBD.csv` 的公式不可盡信**。大燈那組 CSV 寫 `G/12`、`H/12`，
  實車證實 G 與 H 標反了，而且是位元遮罩不是除法。

### 已知限制

- **家族探索有涵蓋缺口**。只試每個家族的 `00` 與 `01` 兩個索引，
  512 次探測涵蓋 65536 個位址。某族成員從 `05` 才開始就會整族漏掉。
  原生 CAN 介面上一次請求約 10 毫秒，單一模組全空間掃描約 11 分鐘，
  那時候這個缺口就消失了。目前 ELM327 約 200 毫秒，全掃要 3.6 小時。
- **`ATH0` 分不出誰回應**。多模組情境只能靠聯集，沒辦法歸屬。
  要歸屬得改 `ATH1`，但那樣 ISO-TP 多幀就得自己組裝。
- **車身總線看不到**。OBD 接頭接的是動力系統總線，閘道器只轉發診斷
  請求、不轉發車身廣播。所以被動監聽在這個接點上抓不到車身訊號，
  換什麼硬體都一樣。要拿到得從車身模組接頭接，侵入性高很多。
- **Mac 必須在車上**。這是這套方案唯一的實體成本。

### 下一階段（尚未決定要不要做）

原生 CAN 介面：ESP32 加 SN65HVD230 收發器，或直接買 USB 轉 CAN 線材。

- 速度快 20 倍，單次請求從 200 毫秒降到約 10 毫秒
- 一張完整快照從 124 秒降到約 6 秒
- **收發器模組上的 120 歐姆終端電阻必須拔掉**。車上總線兩端已經有終端，
  再並一顆會讓阻抗掉到 40 歐姆左右，干擾整條匯流排上的其他模組。
- **一定要用 listen-only 模式**。速率設錯又不是唯讀的話，控制器會往
  總線上狂送錯誤訊框，那是真的會出事。
