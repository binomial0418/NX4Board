# NX4Board OBD 代碼總表

車輛：Hyundai 油電，車系代號 NX4，變速箱零件號 95441-3D210。

這份是唯一的代碼權威來源。每一條都標明**驗證強度**：

- **已上線**：Flutter App 正在用，實車運作正常
- **已驗證**：實車比對確認，但還沒接進 App
- **候選**：有觀察但證據不足
- **否定**：查過了，確定不是那樣，不要再回頭

byte 標號沿用 `OBD.csv` 的慣例：A 是 payload 第一個位元組，
超過 Z 接 AA、AB（試算表欄位進位）。`idx` 是從 0 起算的索引。

## 一、ELM327 初始化序列

App 與 obdlab 使用同一套，行為才對得起來。

| 指令 | 作用 | 為什麼需要 |
|---|---|---|
| `ATZ` | 重置 | 回到已知狀態，約需 1 秒 |
| `ATE0` | 關回音 | 否則每道指令都被回吐一次 |
| `ATL0` | 關換行 | |
| `ATH0` | 關 Header | 讓 ELM 自己做 ISO-TP 多幀組裝 |
| `ATS0` | 關空格 | 回應變成連續十六進位好解析 |
| `ATAL` | 允許長訊息 | **關鍵**。沒有它長回應會被截斷 |
| `ATST32` | 逾時 0x32×4ms ≈ 200ms | 不支援的 DID 才能快速回 NO DATA |
| `ATAT1` | 自動調整時序 | |
| `ATSP6` | 鎖定 ISO 15765-4 CAN 11-bit 500K | 省掉自動偵測 |

`ATH0` 的代價：多顆模組同時回應時分不出是誰回的。查 `0100` 這種廣播
支援表時必須把所有 `41xx` 出現處的點陣圖**聯集**起來，不能只取第一個。

## 二、標準 PID（Mode 01，Header 7DF）

用 obdlab 經 BLE 問出的完整支援表，**六顆模組的點陣圖聯集**，共 49 個：

```
01 03 04 06 07 0B 0C 0D 0E 0F 10 11 13 15 1C 1F 20 21 23 2C 2D 2E 30 31
33 34 3C 40 41 42 43 44 45 46 47 49 4A 4C 51 55 56 5B 5E 60 67 6B 80 9A 9D
```

| 區間 | 回應模組數 | 聯集點陣圖 |
|---|---|---|
| `0100` | 6 | `0xB63FA813` |
| `0120` | 6 | `0xA01DB011` |
| `0140` | 4 | `0xFED08C25` |
| `0160` | 2 | `0x02200001` |
| `0180` | 2 | `0x00000048` |

### 更正：先前對 010B / 010D / 0133 的「否定」是錯的

App 的支援表掃描只讀**第一顆回應模組**的點陣圖，那顆是 `0x80100001`，
只含 PID 01、0C、20。據此下的結論是「MAP 與大氣壓都不支援」，
並寫進了文件與 commit 訊息。實際聯集是 `0xB63FA813`，**三個都支援**。

連帶更正：先前說 `indexOf('0B')` 那個字串搜尋的錯誤是增壓數值憑空生成的
原因，也不成立。那個錯只在回應裡**沒有** `0B` 時才會誤觸，而 `0B` 既然
支援就一定會回，`410B…` 的簽章就在開頭，`indexOf` 找到的位置是對的。
改成逐段走訪仍然是正確的強化（某顆 ECU 省略某個 PID 時才不會出錯），
但它沒有修好增壓，因為增壓本來就不是壞在那裡。

### App 正在使用

| PID | 用途 | 解析 | 狀態 |
|---|---|---|---|
| `010B` | MAP 進氣歧管絕對壓力 | `A` kPa | 已上線 |
| `010C` | 轉速 | `((A<<8)\|B) / 4` | 已上線 |
| `010D` | 車速 | `A` km/h | 已上線 |
| `0133` | 大氣壓 | `A` kPa | 已上線 |
| `015B` | 油電電池 SOC | `A × 100 / 255` | 已上線 |
| `0167` | 水溫 | 3 byte，取 **B** 減 40（A 是感測器遮罩） | 已上線 |

App 送的是合併查詢 `010B0C0D`，照 PID 的固定長度逐段走訪
（`0B`=1、`0C`=2、`0D`=1），不用字串搜尋定位。

### 支援但還沒用的（不需要任何逆向，直接問就有）

| PID | 內容 | 為什麼值得接 |
|---|---|---|
| `0111` | 節氣門位置 | 判斷 MAP 何時等於**中冷管壓力**。實測全放開是 18%，不是 0% |
| `0145` | 相對節氣門位置 | 這個放開時才接近 0%，要判斷全開用它比 `0111` 好 |
| `015E` | 引擎耗油率 | 油電儀表最有感的數字之一 |
| `019A` | 油電電池組資料 | 這台是油電車，值得看內容 |
| `0110` | MAF 空氣流量 | 配合轉速可推算負載 |
| `0143` | 絕對負載 | 正規化過的負載值 |
| `0142` | 控制模組電壓 | 目前電壓是從 `22B002` 拿的，這個更直接 |
| `010F` `0146` | 進氣溫度、環境溫度 | |
| `0104` `0145` `0147` `0149` `014A` `014C` | 負載、節氣門、油門踏板各版本 | |
| `0106` `0107` | 短期與長期燃油修正 | |
| `0121` `0130` `0131` | MIL 里程、清除次數與里程 | |

### 確定不支援

`0170` 專用增壓壓力、`0174` 渦輪轉速、`0187` 歧管壓力多感測器都不在
聯集清單裡。**這台車沒有現成的增壓 PID**，只能靠 MAP 推算。

### MAP 當增壓用，到底準不準

先前這份文件寫「MAP 推算先天就不準」，那個說法要修正。

**MAP 量的是進氣歧管壓力，而那正是引擎實際吸進去的空氣壓力。** 市售增壓錶
絕大多數就是接歧管，顯示的就是這個值。它不是中冷管壓力的近似值，
它是一個意義明確、而且對駕駛更有意義的量：引擎現在呼吸到多少壓力。

兩者只有在節氣門部分開啟時會分離，中冷管壓力高於歧管壓力。但那種狀況下
引擎本來就沒有輸出中冷管壓力所暗示的動力，所以顯示歧管壓力並沒有錯。

真正的限制有四個，前三個可修：

| 限制 | 實測 | 可否改善 |
|---|---|---|
| 零點偏差 | 熄火時 MAP 99、大氣壓 101，差 2 kPa | 可修，轉速為 0 時抓差值歸零 |
| 大氣壓更新 | 其實已經處理：GPS 高度變化超過 50 m 就重讀 | 已妥，先前這裡寫錯 |
| 取樣率 | BLE 約 313 ms 一筆 | 可改善，合併查詢已在做 |
| 解析度 | 單一位元組 1 kPa = 0.01 Bar | 先天限制，但顯示改一位小數即可 |
| 顯示精度 | 儀表用 `toStringAsFixed(2)`，每一格量化誤差都看得見 | 可修 |

解析度那項其實夠用。1.6 T-GDI 的增壓範圍大約 0 到 1.0 Bar，1 kPa 一格
等於 100 階。會覺得跳是因為顯示到小數第二位，改成一位小數或加輕度平滑
就看不出來了。

**要更高解析度只有一條路**：`7E0` 的 123 個 DID 裡找原廠的 16 位元壓力欄位。
這件事現在變得容易，因為我們有 `010B` 當**連續的對照訊號** —— 邊開邊記錄，
找哪個 16 位元欄位跟 MAP 呈線性關係即可。比找離散旗標簡單得多。

## 三、擴充 DID（Mode 22）

這台車的 78 條擴充 PID **全部是 Mode 22**，Mode 21 是零條。
第一版押 `2101` 全無回應就是這個原因。

### 3.1 儀表 CLU — Header 7C6

**`22B002`** 已上線。實例 `E000000019AC009CF5000000AAAAAAAAAA`

| byte | idx | 內容 | 公式 | 驗算 |
|---|---|---|---|---|
| E | 4 | 油量 | 原始值，取 5 筆去頭尾平均 | 0x19 = 25 |
| F | 5 | 電瓶電壓 | `× 0.078125` | 0xAC → 13.44 V |
| G H I | 6-8 | 總里程 | 24 bit 大端，單位 km | 40181 km |
| J K | 9-10 | 保養剩餘里程 | 16 bit 大端 | |
| L M | 11-12 | 保養剩餘天數 | 16 bit 大端 | |

> 注意：程式裡那四個區域變數叫 `byteG`~`byteJ`，但實際讀的是
> idx 9-12，也就是標號 J~M。變數命名與 CSV 標號不一致，改動時容易搞錯。

**770 家族尚未解讀的位址**：`BC01` `BC05` `BC07` `BC10` 完全未解，
`BCFC`（全零）`BCFD`（90 byte 感測器陣列）`BCFF`（字串 "3520"）用途不明。
其中三個位元組已知會動但沒有解釋，是雨刷等開關的首要嫌疑：

| DID | byte | 觀察到的值 |
|---|---|---|
| `22BC05` | F (idx 5) | `0x40` / `0x00` |
| `22BC10` | E (idx 4) | `0xF0` / `0x00`，一次四個位元 |
| `22BC10` | F (idx 5) | `0x20` / `0x00` |

其餘已知：`22B000`、`22B001`、`22B003` 有回應但用途未解。
CLU 整族只有這四個，**PRND 雖然顯示在儀表上但沒有暴露出來**。

### 3.2 車身 IGMP — Header 770

家族 `22BCxx`，已知有回應：`BC01 BC03 BC04 BC05 BC06 BC07 BC08 BC09 BC10 BCFC BCFD BCFF`

| DID | byte | idx | 遮罩 | 意義 | 狀態 |
|---|---|---|---|---|---|
| `22BC03` | E | 4 | `0x20` | 駕駛座車門開 | 已上線 |
| `22BC03` | E | 4 | `0x01/0x04/0x10/0x80` | 左後 / 右後 / 右前 / 尾門 | 已上線 |
| `22BC04` | E | 4 | `0x08` 或 `0x04` | 未上鎖（只有前兩門有訊號） | 已上線 |
| `22BC06` | E | 4 | `0x2D` | **踩煞車** | 已驗證 |
| `22BC08` | F | 5 | `0x08` | **倒車 R 檔** | 已上線 |
| `22BC08` | F | 5 | `0x02` | 疑似室內燈 | 候選 |
| `22BC09` | G | 6 | `0xC0` | 大燈總開關（見下方保留意見） | 已上線 |
| `22BC09` | H | 7 | `0x03` | 遠燈 | 已上線 |
| `22BC09` | F | 5 | `0x04` | 門鎖或設防，**不是燈** | 候選 |
| `22BC10` | F | 5 | `0x20` | 疑似防盜設防 | 候選 |
| `22BC09` | G | 6 | `0x80`? | **小燈，待驗證** | 待查 |
| ? | ? | ? | ? | **後霧燈，位置未知** | 待查 |
| `22BC05`/`22BC10`? | F / E | — | — | **雨刷開關，多位置欄位** | 待查 |

Header 探測歷史：`ATSH302` 曾是候選，實車 11 次查詢全部 NO DATA，已淘汰。
現在只用 `770`，由輪詢自動鎖定。

**大燈那組的教訓**：`OBD.csv` 寫 `High_Beam = G/12`、`Low_Beam = H/12`，
實車比對後標註是反的，而且不是除法而是位元遮罩。CSV 的公式不可盡信。

**byte G 那兩個位元還沒拆開**。遮罩 `0xC0` 其實是 bit 7 與 bit 6，
所有樣本裡它們一直同進同出，但那可能只是因為**從來沒有取樣過只開小燈的
狀態**。樣本不是全暗就是大燈全開，兩個位元當然一起動。如果 bit 7 是小燈、
bit 6 是近燈，現在的 `(g & 0xC0) != 0` 會讓「只開小燈」被誤報成大燈開啟，
連帶讓 ESP32 儀表的亮度提前變暗。轉到只有小燈那一段讀一次就能定案。

**byte F 不是燈，已排除。** 它在 `00` 與 `04` 之間變，一度像小燈，
但有一筆樣本是大燈開著而 F=00（傍晚掃描 `322003CC4000C000`），
而程式註解裡大燈開的樣本是 F=04。小燈不可能在大燈亮時熄滅，所以 F 與燈無關。
比較像門鎖或設防：行駛中車門會自動上鎖，那兩筆大燈開的樣本應該是行駛中拍的。

**煞車的驗證**：三次切檔標記之後 2.4 / 4.7 / 4.9 秒亮起，踩住 7 至 20 秒，
標記之間另有幾次獨立按壓。`0x2D` = bit 0,2,3,5 同時亮，
應該是一群煞車相關輸出（煞車燈、高位煞車燈、煞車開關）同進同出，
與大燈那組 bit 7+6 同進同出的形態一致。

| byte | idx | 輪胎 | 公式 | 驗算 |

## 四、否定結果

不要再回頭查這些。

**鑰匙是否在車內，不在 770。** 車輛 READY、駕駛門開著，人帶鑰匙走遠到
車輛發出無鑰匙警示再走回，全程 236 秒。BC01~BC10 九個位址在那段時間
一個 byte 都沒變，取樣一輪約 2 秒、涵蓋上百輪。乾淨的否定，不是取樣不足。

**7A5 不存在。** 兩次點名，含接受負回應的版本，都毫無反應。

**沒有專用增壓 PID。** `0170`/`0174`/`0187` 都不支援。增壓只能從
`7E0` 的 123 個 DID 裡找，或者放棄。

**`22E017` byte Q 不是 N 檔。** 先前快照顯示 P/R/D=0x11、N=0x10 很像，
但後續整場都是 0x5B 沒動過，是會隨工況變的量值不是旗標。

**`22BC04` byte E 不是倒車。** 這是 `OBD.csv` 的 `IGMP_Reverse` 給的線索，
實車證實那個 byte 整場不動，它是門鎖。真正的倒車在 `22BC08`。

**P 與 N 分不出來。** 兩者在所有已知旗標上都是 0，只能回報「P 或 N」。

## 五、車輛特性備忘

**油電車。** READY 狀態下引擎熄火、轉速 0 是正常的。不能拿轉速判斷車有沒有
發動，也不能拿它當「引擎運轉」的旗標。

**擴充 PID 全是 Mode 22。** Mode 21 零條。

**多顆模組回應廣播查詢。** `0100` 這種會有好幾顆各自回自己的支援表，
必須聯集。只取第一個會漏掉大半。

**負回應代表存在。** `7F 22 31`（要求超出範圍）表示模組聽到了也答了，
只是不支援這個 DID。點名時必須跟正回應一樣算數，否則 `770` 會被判成不存在。

**家族探索有涵蓋缺口。** 現行做法只試每個家族的 `00` 與 `01` 兩個索引，
512 次探測涵蓋 65536 個可能位址。如果某族成員從 `05` 才開始，整族會漏掉。
前雷達只找到 5 個一到兩位元組的小值，很可能就是這個原因。
