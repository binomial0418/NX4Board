# Nissan March K13：OBD／胎壓可行性評估與研究流程

評估日期：2026-10-02。目標車款是 Nissan March K13（台灣裕隆版）。

**做法：先用 obdlab 在 K13 上把代碼對應表做出來，確認後再把 NX4Board 的 OBD 層
重構成「車型設定檔」，加入 K13。** 研究階段不寫 App，理由見 README「為什麼要繞過 App」。

目標資料：車速、轉速、水溫、里程、剩餘油量、TPMS（胎壓及感測器電壓）。

## 結論總表

| 項目 | 讀取方式 | 可行性 | 待確認 |
|---|---|---|---|
| 車速 | 標準 `010D`；備案廣播 `0x284` | 幾乎確定 | — |
| 轉速 | 標準 `010C`；備案廣播 `0x180` | 幾乎確定 | — |
| 水溫 | 標準 `0105`；備案廣播 `0x551` | 幾乎確定 | — |
| 里程 | 被動監聽廣播 `0x5C5` byte B–D | 高 | 對照儀表 |
| 剩餘油量 | `012F` 或廣播封包 | 中 | ECM 是否支援 `012F`；廣播位置有矛盾 |
| 胎壓（四輪） | BCM `745→765` 診斷查詢 | 中高 | 讀取指令編號與公式要實車掃出 |
| 感測器電壓 | OBD 讀不到；無線直收也多半只有電量低旗標 | 低 | 見「無線直收」 |

## 一、CAN 架構

- 同時期 Nissan（Qashqai J10、Juke F15、Leaf、370Z，K13 同代）全車只有**一條主 CAN（500 kbps、11-bit）**，OBD 座直接接在上面、沒有閘道器。所以除了主動查詢，還能**被動監聽**各模組的廣播。
- 診斷位址（Nissan 各車型一致）：

| 模組 | 請求 | 回應 |
|---|---|---|
| ECM 引擎 | `7E0` | `7E8` |
| 儀表（Meter） | `743` | `763` |
| BCM（含胎壓） | `745` | `765` |
| IPDM-E/R | `74D` | — |

- BCM／IPDM 的診斷通常要先送 `10 C0` 進入診斷模式。
- Qashqai 文件裡那份 ECM 的 `22 2xxx` 清單是 **Renault K9K 柴油引擎**（聯盟共用引擎）的格式，K13 是 Nissan 自家的 HR12DE／HR15DE，**不能直接套用**。

## 二、廣播封包（來自其他 Nissan 車型，K13 要驗證）

位元標記沿用 Qashqai 文件：byte 1–8 記為 A–H，bit 8 是 MSB。

| ID | 內容 | 位置與公式 | 來源 |
|---|---|---|---|
| `0x180` | 轉速 | A–B，15-bit，0.25 rpm/LSB（Juke 設定檔寫 ÷7，要實測） | Qashqai、Juke |
| `0x280` | 車速（儀表） | E–F，0.01 km/h | Qashqai、Leaf |
| `0x284` | 車速（ABS） | E–F，0.01 km/h；A–D 是前輪輪速，0.005 km/h | Qashqai、Leaf |
| `0x551` | 水溫 | A − 40 °C | Qashqai、Juke |
| `0x5C5` | 里程 | B–D，24-bit，km | Leaf、Qashqai、Juke 三份一致 |
| `0x5C5` | 油量？ | Juke 設定檔寫 byte A（255→0 對應 0–45 L）；Qashqai 說 byte A 是手煞車等狀態位元。**兩份矛盾** | Juke vs Qashqai |
| `0x2DE` | 剩餘可跑里程 | G–H，0.1 km | Qashqai |
| `0x54C` | 剩餘可跑里程 | — | Juke |
| `0x60D` | 車門與 IGN 狀態 | B.2–B.3 是 IGN 狀態（OFF／ACC／ON／START） | Qashqai |
| `0x385` | 四輪胎壓 | C–F，0.25 psi/LSB | Leaf。**K13 儀表不顯示胎壓數值，BCM 可能不廣播這個封包** |

ELM327 監聽方式：`ATCRA <id>` 加 `ATMA`，一次只收一個 ID，避免藍牙緩衝區塞爆（BUFFER FULL）。obdlab 的 `listen` 就是這樣做的；NX4Board App 目前只有「下指令、等回應」的輪詢模式，整合時要另外加監聽模式。

## 三、胎壓：BCM 診斷查詢

- 台灣版 K13 **有原廠 TPMS，儀表只亮異常警示燈、不顯示數值**（使用者確認）。
- 是**直接式**：輪圈裡有感測器，市面有副廠替換品。原廠料號 **40700-3HN0B = Pacific PMV-CA74，433 MHz**。
- Nissan 原廠維修手冊（2016 370Z WT 章節，370Z 的儀表也只亮警示燈）裡，BCM「AIR PRESSURE MONITOR」的資料監看項目：

| 項目 | 單位 |
|---|---|
| AIR PRESS FL / FR / RR / RL | kPa、kg/cm²、psi |
| ID REGST FL1 … RL1 | Done / Yet |
| WARNING LAMP | On / Off |
| BUZZER | On / Off |

  **沒有感測器電池或電壓的項目。** 手冊另外寫「停車 5 分鐘內讀取 DATA MONITOR」，表示 BCM 會保留最後一次收到的值。
- 讀取指令的編號網路上查不到，要實車掃描：obdlab `sweep 745 --sid 21`（KWP 的 `2100`～`21FF`），必要時再試 22 家族。
- 找位置的方法：四輪打成不同壓力（例如 32、33、34、35 psi），開一小段路讓感測器送出訊號，停車後掃描，找出剛好對應這四個值的四個位元組。

## 四、胎壓：無線直收（選配，為了電池狀態）

- 感測器大約每分鐘用 433 MHz 送一次資料，停車時幾乎不送。車內另外接收即可，只收不發，不影響原廠系統。
- rtl_433 的 Nissan 解碼器（`tpms_nissan.c`，`-R 248`，來源是 Leaf）解出的格式只有 37 位元：

  `MODE:3 | ID:24 | 胎壓:8（raw/4 − 3 psi） | UNKNOWN:2`

  **沒有溫度、沒有電壓。** 電量低旗標最可能藏在 MODE 或 UNKNOWN 裡，可以拿一顆快沒電的舊感測器對照（K13 的原廠感測器多半已經 8 年以上）。
- 尚未確認：K13 的 PMV-CA74（433 MHz）和 Leaf（美規多半 315 MHz）是不是同一套格式。
- 硬體：
  1. **RTL-SDR（約 NT$1,000）+ rtl_433 先探路**：`rtl_433 -f 433.92M -s 1000k -R 248`；解不出來就用 `-A` 分析原始波形。
  2. 確認格式後再做 **ESP32 + CC1101（約 NT$300）車載版**：FSK、約 8.3 kbaud、Manchester，前導碼 `F5 55 55 55 E`。資料可接進現有 ESP32 面板的 WebSocket／序列埠協定。
- 注意事項：
  - 收到的只有 ID，要建一次 ID 與輪胎位置的對照（放一輪的氣，或讀 BCM 的 ID 註冊），換輪胎或對調後要重做。
  - 會收到旁邊車的感測器，只收已登記的 4 個 ID。
  - 大約一分鐘一筆，要顯示資料多久以前收到。

## 五、obdlab 研究流程

所有指令都在 `obdlab/` 下執行，加 `--car k13`：模組位址用 Nissan 的表，資料存在 `data/k13/`（不進版控，裡面會有 VIN）。

### 這次為 Nissan 補上的功能

| 功能 | 為什麼 |
|---|---|
| 車型設定（`cars.py`、`--car`） | 模組位址表、點名方式、廣播假設、資料夾都分車型；預設仍是 `nx4`，行為不變 |
| 回應位址與流量控制（`uds.select_module`） | Nissan 回應不是請求 +8（745→765）。不設 `ATCRA` 回應會被濾掉；不設 `ATFCSH` 多幀流量控制會送到 765−8=75D，長回應只剩第一幀 |
| 診斷會談（`--session C0`） | BCM／儀表的資料多半要先進 `10 C0`。每個模組閒置超過 2 秒就重進。會談不是寫入，逾時自己回預設 |
| `21xx` 掃描（`sweep 745 --sid 21`） | 這一代 Nissan 講 KWP，資料在 `21 xx`。結束時印負回應統計，全是會談類原因就提示加 `--session` |
| 位址普查（`census`） | 回應位址不規則（Leaf 的 TCU 746→783），700~7FF 每個送 `3E01`、放寬接收過濾，從回應行首看是誰回的。結果存 `census.json`，之後自動套用 |
| 被動監聽（`listen`） | 一次聽一個 ID 幾秒，印會變的 byte 與假設解讀；不帶 ID 則不過濾聽一下列出匯流排上的 ID |
| BLE 連線 | 不給 `--port` 就走 BLE（`--ble-name`，預設 VLINK） |

邏輯用模擬 ELM 測過（位址切換、會談、21 掃描、普查、監聽解析），**還沒上過實車**。

### 第一趟：電門 ON、引擎發動、停在原地（約 20 分鐘）

```bash
python3 run.py --car k13 pids                  # 標準 PID，重點看 012F（油量）
python3 run.py --car k13 listen --seconds 3    # 匯流排上有哪些 ID；沒聽到 = 有閘道器，被動這條路不通
python3 run.py --car k13 listen all            # 逐一聽設定裡的廣播假設，對照儀表
python3 run.py --car k13 census                # 700~7FF 誰在、回應位址是多少
python3 run.py --car k13 modules               # 用普查結果點名，2180 會回零件號
```

判讀重點：
- `listen all` 的 `5C5` 假設解讀 B–D 應等於儀表里程；`551` 的 A−40 對照水溫；`180` 兩個除數看哪個對儀表轉速
- `census` 裡 `745→765`、`743→763` 要出現；沒出現先試 `--session C0` 再點名

### 第二趟：找胎壓

1. 四輪打成不同壓力（例如 FL 32、FR 33、RR 34、RL 35 psi），開一小段路讓感測器送出訊號
2. 停車（5 分鐘內，BCM 還保留數值），掃描：
   ```bash
   python3 run.py --car k13 sweep 745 --sid 21
   python3 run.py --car k13 sweep 745 --sid 21 --session C0   # 上一行全被拒時
   ```
3. 找出 payload 裡剛好對應四個壓力的四個位元組（kPa、psi×4 或 kPa×4 之類的比例都要試）
4. 確認後改兩輪的壓力再拍快照比對：`snap 胎壓A` ×2、`snap 胎壓B` ×2、`diff`

### 第三趟：油量

- `012F` 不支援時：加油前後各 `listen 5C5` 看 byte A；再對 `743` 掃 `--sid 21` 拍「加油前／後」快照比對

### 每趟順手做

- 熄火 → ACC → ON 各跑一次 `listen --seconds 3`，記下 ACC 時哪些 ID 還在送
- 結果寫進本文件第七節的代碼對應表

## 六、整合回 NX4Board

代碼表確認後才動 App：
1. 先重構、不改行為：把 `ObdSppService` 的 Hyundai 邏輯搬進「NX4 設定檔」，連線層（藍牙、ELM 初始化、佇列）共用。NX4 實車驗證沒退步再往下
2. 加 K13 設定檔：輪詢清單、被動監聽清單、有哪些資料（沒有的欄位給 null，UI 與 ESP32 面板隱藏）
3. 設定頁選車型，之後可用 VIN（`0902`）自動判斷
4. Hyundai 專用的功能（HEV SOC、BMS `7E4`、檔位探測、OBD.csv）在 K13 上沒有對應，設定檔標為不支援

## 七、實車紀錄

### 2026-10-02 第一趟（停車怠速 → 市區約 6 公里）

**傳輸器「OBDII」**（白牌 ELM327 v1.5，經典藍牙＋BLE 雙模）
- 經典藍牙序列埠 `/dev/cu.OBDII` 跟 Vlink 一樣連不上，**BLE 可以**：服務 `FFF0`。`ble.py` 已改成自動辨識 18F0／FFF0／FFE0，用 `--ble-name OBDII`
- **`ATCRA` 無效**（回 OK 但不過濾），改用 `ATCF <回應> + ATCM 7FF` 才收得到 Nissan 的回應
- **`ATFCSH` 也很可能無效**，但目前沒遇到需要它的多幀回應
- **鎖位址**：第一個成功回話的模組會把 Header 鎖死，之後 `ATSH` 回 OK 但不生效，`ATWS`、`ATPC` 都解不開，只有 `ATZ` 可以。→ **一條連線只問一個模組**，換模組要 `ATZ` 重來
- `ATMA` 聽不到任何東西（引擎發動中，連 0 幀）。分不出是這顆傳輸器的監聽壞了，還是 K13 的 OBD 接頭後面沒有廣播流量
- 原始模式 `ATCAF0` 可用，但幀要送 3 byte（`022140`），補到 8 byte 模組不回

**標準 PID**（ECM 7E8）：`01 03 04 05 06 07 0C 0D 0E 0F 10 11 13 15 1C 1F 20 21 24 2E 30 31 3C 40 41 42 43 44 45 47 49 4A 4C 4D 4E 51`
- 車速 `010D`、轉速 `010C`、水溫 `0105` 都有
- **油量 `012F` 不支援**
- Mode 09 只有 `04`（校正碼 `11HN2A…`）與 `06`，**沒有 VIN**

**位址普查**（3E01，700–7FF）

| 請求 | 回應 | 身分 | 備註 |
|---|---|---|---|
| `71D` / `71E` | `72D` / `72E` | 未知（UDS，3E01 回 NRC 11） | |
| `740` | `760` | ABS | |
| `742` | `762` | EPS | |
| `743` | `763` | 儀表 | KWP，`10C0` 可進 |
| `745` | `765` | BCM | KWP，`10C0` 可進；**不支援 22 服務** |
| `74D` | `76D` | IPDM E/R | |
| `758` | `778` | 未知 | 只有 `2100` |
| （補） | | | 用 `1081` 重做普查，結果相同：沒有藏起來的模組 |
| `7E0` | `7E8` | 引擎 ECM | 要進 `10C0`；資料在 `22 11xx/12xx/13xx/15xx`，見下 |
| `7E1` | `7E9` | 變速箱 | |

**BCM `21xx`**（有回應的：`00 04 20 21 40 41 44 4C 50 51`）
- `2144` byte B–C ÷ 100 = **車速 km/h**（市區 0→29→0 吻合）
- `2141`、`214C`、`2151` 有單一位元每幾秒翻轉（像方向燈或開關），待標記
- `2140` = `DF DD 80 00` 整趟不變。DF/DD 換成 kPa 是 32.3／32.0 psi，接近前輪但不會隨胎溫變，**判定不是即時胎壓**
- `2142`–`2149` 等 18 個：完全沉默（原始模式也是），不存在

**儀表 `21xx`**：只有 `2100` = `E0 00 00 00`

### 2026-10-02 第一趟（續）：停車、電門 ON、引擎發動

**ECM（7E0）在 `10 C0` 會談裡**
- `21xx` 只有 `2100`–`2105`，幾乎都是 0；`21F0` 是多幀的 ECU 識別（含 `2JCS62D8`）——證明這顆傳輸器對 ECM 的多幀沒問題
- **`22` 服務有 4 個家族**：`11xx`、`12xx`、`13xx`、`15xx`。`xx00`、`xx20`… 回的是支援清單位元圖（規則同 `0100`），共 58 個項目，全部讀過存在 `data/k13/ecm_cids.json`
- **會談中 ECM 拒絕標準 PID**（`7F 01 80`），回 `1081` 預設會談後才恢復。App 要二選一或來回切
- 怠速 → 約 2000 轉 → 怠速的錄製（`data/k13/ecmrec_*.json`）判讀：

| CID | 讀值 | 解讀 | 依據 |
|---|---|---|---|
| `221201` | 65 → 158 → 71 | **轉速 = 值 × 12.5** | Nissan CONSULT 傳統單位，踩油門時吻合 |
| `221101` | 136 | **水溫 = 值 − 50**（86 °C） | 同時讀 `0105` 得 87 °C |
| `221103` | 175 | **電瓶電壓 = 值 × 0.08**（14.0 V） | 與 `ATRV` 14.0 V 完全吻合 |
| `221209`、`221219`、`22120D/0E` | 踩油門時跳 | 負荷／噴油／點火類 | 不需要 |
| `22111A`=28、`221147`=88、`221148`=112、`221249`=60、`22121B`、`22121C`… | 整段不變 | **油量感知器電壓的候選** | 停車時油量不變，要配合油表位置或加油前後比對 |

**`2C`（動態定義讀取）**：ECM 回 `7F 2C 12`、儀表回 `7F 2C 11`，都不支援，這條路關閉。

**儀表（743）**：`22` 不支援（`7F 22 11`）、`2C` 不支援，只有 `2100`。**里程無法從儀表診斷讀出。**

**`71D`／`71E`**：也講 KWP（`22` 不支援，`2180` 要會談）。會談內的 `21xx` 掃描跑到一半傳輸器斷線，**下次補掃**。

**胎壓仍未找到。** 已排除：BCM 全部 `21xx`、BCM `22` 服務（不支援）、`758`。剩下的可能：
1. `71D`／`71E` 會談內的 `21xx`（未掃完）
2. ~~動態定義 `2C`~~：ECM 與儀表都不支援
3. ~~普查漏掉的模組~~：`1081` 重做普查，沒有新模組
4. 走 433 MHz 直收（第四節）——目前最可能的路

里程：儀表診斷讀不到。務實做法是 App 端讓使用者輸入一次目前里程，之後用車速積分累加。
